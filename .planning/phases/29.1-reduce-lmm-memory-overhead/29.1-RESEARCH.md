# Phase 29.1: Reduce LMM Memory Overhead - Research

**Researched:** 2026-02-15
**Domain:** NumPy memory management, BLAS transpose optimization, Python garbage collection
**Confidence:** HIGH

## Summary

This phase targets three specific memory optimizations in the LMM pipeline: eliminating the redundant `UT = np.ascontiguousarray(U.T)` copy, freeing the kinship matrix immediately after eigendecomposition, and forcing garbage collection between pipeline phases. At 125k samples, the eigenvector matrix U is 125 GB, so the contiguous transpose copy creates 125 GB of unnecessary overhead.

The most important finding is that **numpy's `@` operator already detects F-contiguous arrays (like `U.T`) and passes `CblasTrans` to BLAS internally**, verified from numpy's source code in `cblasfuncs.c` and `matmul.c.src`. This means `U.T @ x` has identical BLAS performance to `UT @ x` where `UT = np.ascontiguousarray(U.T)` -- the 125 GB copy is pure waste. The fix is to delete `UT` and use `U.T` directly in all matmul operations.

The kinship matrix freeing is already partially implemented in `runner_streaming.py` (lines 347-349) but missing from `runner_jax.py`. The `gc.collect()` call is present in `runner_streaming.py` after kinship deletion but should be expanded to cover LAPACK workspace cleanup.

**Primary recommendation:** Replace `UT = np.ascontiguousarray(U.T)` with direct `U.T` usage in all three files (`runner_jax.py`, `runner_streaming.py`, `loco.py`), add `del kinship; gc.collect()` in `runner_jax.py` after eigendecomp, and ensure `gc.collect()` runs after eigendecomp in `_eigendecompose_or_reuse`.

## Architecture Patterns

### Pattern 1: Direct Transpose View for BLAS Operations
**What:** Use `U.T @ x` directly instead of `np.ascontiguousarray(U.T) @ x`
**When to use:** Always, for matrix-vector and matrix-matrix products where one operand is a transpose
**Why it works:** NumPy's `@` operator (both `np.dot` via `cblasfuncs.c` and `np.matmul` via `matmul.c.src`) detects F-contiguous arrays and passes `CblasTrans` to `cblas_dgemm` instead of copying to C-contiguous order.

**Before (current code, wastes 125 GB at 125k samples):**
```python
# runner_jax.py line 183
UT = np.ascontiguousarray(U.T)  # <-- 125 GB copy

with blas_threads():
    UtW = UT @ W
    Uty = UT @ phenotypes
# ... later in _prepare_chunk:
    UtG_chunk = np.ascontiguousarray(UT @ geno_chunk)
```

**After (zero-copy, identical BLAS performance):**
```python
# No UT allocation needed - U.T is an F-contiguous view (0 bytes)

with blas_threads():
    UtW = U.T @ W       # numpy detects F-contiguous U.T, passes CblasTrans
    Uty = U.T @ phenotypes
# ... later in _prepare_chunk:
    UtG_chunk = np.ascontiguousarray(U.T @ geno_chunk)
```

Note: `np.ascontiguousarray` on the RESULT `UtG_chunk` is still needed because the result must be C-contiguous for JAX device_put. But `U.T` itself needs no copy.

### Pattern 2: Eager Kinship Deletion After Eigendecomp
**What:** Delete the kinship matrix immediately after eigendecomposition returns, before any other allocations
**When to use:** In all LMM runners after `_eigendecompose_or_reuse` returns

**Before (`runner_jax.py` -- kinship never explicitly freed):**
```python
eigenvalues_np, U = _eigendecompose_or_reuse(kinship, ...)
UT = np.ascontiguousarray(U.T)  # kinship still in memory!
```

**After:**
```python
eigenvalues_np, U = _eigendecompose_or_reuse(kinship, ...)
del kinship  # Free n^2*8 bytes immediately
gc.collect()  # Force LAPACK workspace + kinship release to OS
```

### Pattern 3: GC Collection at Phase Boundaries
**What:** Call `gc.collect()` after eigendecomposition completes to force release of LAPACK DSYEVD workspace
**When to use:** Between eigendecomp and LMM phases; this prevents DSYEVD workspace (which is ~2*n^2*8 bytes) from overlapping with LMM working set

**Where to add:**
```python
# In _eigendecompose_or_reuse (prepare.py):
eigenvalues_np, U = eigendecompose_kinship(kinship, check_memory=check_memory)
# DSYEVD workspace was allocated by LAPACK, freed when eigh returns,
# but Python GC hasn't necessarily collected it yet
gc.collect()  # Force workspace release before LMM allocations
```

### Anti-Patterns to Avoid
- **Creating UT then referencing U.T:** After removing the `UT` variable, ensure `_prepare_chunk` closures capture `U` not `UT`. If `U` is passed to a nested function or closure, ensure the reference is correct.
- **Deleting kinship when caller still needs it:** In `runner_jax.py`, kinship is a parameter. If the caller might use it after the call, don't delete it. However, inspection shows the pipeline never uses kinship after calling the runner, so this is safe. Use `kinship = None` assignment instead of `del kinship` if the parameter ownership is ambiguous.
- **Assuming gc.collect() returns memory to OS:** On Linux (the target platform for large-scale runs), `gc.collect()` releases Python objects, but the C allocator (glibc malloc) may retain memory in its arena. For LAPACK workspace allocated via malloc, `gc.collect()` triggers Python finalizers which call free(), but glibc may not return pages to OS via `MADV_FREE`/`munmap` unless the freed block is at the top of the heap. In practice, for 100+ GB allocations, glibc uses mmap which IS returned on free. This means gc.collect() is effective for the large allocations we care about.

## Common Pitfalls

### Pitfall 1: Assuming UT.T @ x is Same as U.T @ x
**What goes wrong:** If refactoring introduces `U.T.T` (which is just `U`) instead of `U.T`, the matrix multiplication computes `U @ x` instead of `U^T @ x`, producing completely wrong results.
**Why it happens:** Mechanical find-and-replace of `UT` with `U.T` in expressions like `UT @ x`
**How to avoid:** Replace `UT` with `U.T` only in `@ ` expressions. Double-check each substitution. All existing tests must pass with identical results (no tolerance changes).
**Warning signs:** Any test failure, especially numerical mismatches in beta/se/p-values.

### Pitfall 2: Closure Capture of Deleted Variable
**What goes wrong:** `_prepare_chunk` is a closure in `runner_jax.py` and `runner_streaming.py` that captures `UT` from the enclosing scope. After removing `UT`, the closure must capture `U` and use `U.T` inside the function.
**Why it happens:** The closure references `UT` by name; removing the variable without updating the closure body causes NameError.
**How to avoid:** Search each file for ALL references to `UT` after removing the assignment. The `_prepare_chunk` inner function in both runners uses `UT @ geno_jax_chunk` which must become `U.T @ geno_jax_chunk`.
**Warning signs:** NameError at runtime, test failures.

### Pitfall 3: Deleting Kinship When Pre-computed Eigendecomp Was Used
**What goes wrong:** If eigenvalues/eigenvectors are pre-computed, `_eigendecompose_or_reuse` returns them directly and kinship was never consumed. Calling `del kinship` is fine (it may be None), but `kinship` could also be a view into the caller's data.
**Why it happens:** The runners receive kinship as a parameter; ownership is ambiguous.
**How to avoid:** Check `if kinship is not None: del kinship` before gc.collect(). This pattern is already used correctly in `runner_streaming.py` line 347-349.
**Warning signs:** Caller's kinship variable unexpectedly None (not a risk in practice since pipeline.py doesn't use kinship after calling the runner).

### Pitfall 4: gc.collect() Not Releasing Large LAPACK Allocations
**What goes wrong:** On some platforms/allocators, `gc.collect()` doesn't return memory to the OS even after freeing large arrays.
**Why it happens:** glibc malloc arenas may hold onto freed memory. However, allocations over MMAP_THRESHOLD (~128 KB default, way below our GB-scale allocations) use mmap which IS returned to OS on free.
**How to avoid:** For the 100+ GB LAPACK workspace allocations we care about, glibc uses mmap, so free() returns them to the OS. No special handling needed.
**Warning signs:** RSS not decreasing after gc.collect() -- test with `log_memory_snapshot` before and after.

### Pitfall 5: Double-Buffering Pattern in Chunk Loop
**What goes wrong:** The chunk processing loop uses double-buffering (prepare next chunk while current one computes). The `_prepare_chunk` function uses `UT @` which must be changed to `U.T @`. Both the initial call outside the loop AND the call inside the loop body must be updated.
**Why it happens:** There are two call sites for `_prepare_chunk` -- one before the loop (for the first chunk) and one inside the loop (for the next chunk).
**How to avoid:** Grep for ALL uses of `UT` in each file, not just the assignment.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `np.ascontiguousarray(A.T) @ B` | `A.T @ B` directly | NumPy has supported this since at least v1.16 (CblasTrans detection in cblasfuncs.c) | Eliminates n^2*8 byte copy |
| Manual `scipy.linalg.blas.dgemm(trans_a=1)` | `A.T @ B` via numpy `@` | N/A -- numpy does this automatically | No need for scipy runtime dependency |

**Key insight from numpy source code:**
- `cblasfuncs.c` (for `np.dot`): explicitly checks `PyArray_IS_F_CONTIGUOUS(ap1)` and sets `Trans1 = CblasTrans` with comment "Avoid temporary copies for arrays in Fortran order"
- `matmul.c.src` (for `np.matmul`/`@`): uses `is_blasable2d()` to check both C and F layouts, sets `trans1 = CblasTrans` when F-contiguous

## Open Questions

1. **Performance regression from stride pattern?**
   - What we know: BLAS handles `CblasTrans` natively with no performance penalty for large matrices. For small matrices there might be minor overhead from non-sequential memory access during transpose, but our matrices are 125k x 125k.
   - What's unclear: Whether the specific MKL ILP64 implementation has any corner cases with CblasTrans for very large matrices (>46k).
   - Recommendation: Benchmark before/after on a small test (e.g., 1k samples) to verify numerical identity, then validate at scale on Databricks. No tolerance changes should be needed.

2. **Does `del kinship` in runner_jax.py affect callers?**
   - What we know: `pipeline.py` passes `K` to `run_lmm_association_streaming` and never uses `K` afterward. `run_lmm_association_jax` receives `kinship` as parameter; the caller (`test_runner_jax.py` and validation code) doesn't reuse it after the call.
   - What's unclear: Whether any external users rely on kinship remaining valid after calling the runner.
   - Recommendation: Set `kinship = None` instead of `del kinship` as a defensive pattern -- this breaks the reference without affecting the caller's variable name.

3. **How to measure "peak RSS measurably lower"?**
   - What we know: Existing `log_memory_snapshot` and `log_rss_memory` functions provide RSS snapshots at named checkpoints. The benchmark runs on Databricks with 125k samples.
   - What's unclear: Whether RSS snapshots at fixed checkpoints capture the true peak. Peak may occur transiently during BLAS operations.
   - Recommendation: Add RSS snapshots at these specific points: (a) after eigendecomp, (b) after kinship deletion + gc.collect, (c) before first chunk processing. Compare before/after values. For the UT elimination, the 125 GB difference should be obvious in any snapshot taken during LMM processing.
