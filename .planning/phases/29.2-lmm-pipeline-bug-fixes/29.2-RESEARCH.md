# Phase 29.2: LMM Pipeline Bug Fixes - Research

**Researched:** 2026-02-15
**Domain:** LMM pipeline correctness, robustness, and code hygiene
**Confidence:** HIGH

## Summary

This phase addresses 7 concrete bugs and code issues identified during code review of the LMM pipeline. All issues are in existing code files (`pipeline.py`, `loco.py`, `runner_streaming.py`, `runner_jax.py`, `eigen_io.py`, `test_kinship_benchmark.py`) with clear, localized fixes. No new libraries or architectural changes are required.

The bugs range from correctness issues (eigen file validation ignores covariate filtering, streaming runner produces no output file when all SNPs are filtered) to performance issues (redundant set construction per chromosome, unnecessary `logls_mle` accumulation) to robustness issues (missing `lmm_mode` validation, Docker test raises instead of skipping). All existing tests must continue to pass with identical numerical results.

**Primary recommendation:** Fix each bug independently with its own test, working through them in dependency order. The eigen validation fix (criterion 1) and LOCO chunked reads (criterion 2) are the most impactful.

### Bug-by-Bug Analysis

#### Bug 1: Eigen file validation uses phenotype-filtered count, not covariate-filtered count

**Location:** `pipeline.py` lines 529-534

**Current code:**
```python
# pipeline.py line 455
phenotypes, n_analyzed = self.parse_phenotypes()
# ...
# pipeline.py line 531-534 (step 7, before covariates loaded at step 8)
eigenvalues, eigenvectors = read_eigen_files(
    self.config.eigenvalue_file,
    self.config.eigenvector_file,
    n_samples=n_analyzed,  # BUG: phenotype-only count
)
```

**Problem:** `n_analyzed` counts samples with valid phenotypes (non-NaN, non-(-9)). But covariates are loaded at step 8 (line 571), and the LMM runner further filters samples with NaN covariates (see `runner_streaming.py` lines 189-191). If a covariate file has NaN rows that don't overlap with phenotype NaN rows, the actual sample count used by the runner will be smaller than `n_analyzed`.

Pre-computed eigen files are generated from the valid-sample-filtered kinship matrix (see `pipeline.py` lines 554-558 where `valid_mask` includes both phenotype AND covariate filtering for the write path). So reading them back with phenotype-only `n_analyzed` will fail to catch dimension mismatches.

**Fix approach:** Compute the full `valid_mask` (phenotype + covariate) before the eigen file validation step. Either:
- Load covariates earlier (before step 7)
- Or compute the combined valid_mask and use it for `n_samples` parameter

The cleaner fix is to load covariates earlier (swap steps 7 and 8's covariate portion), then compute `n_valid = int(np.sum(valid_mask))` where `valid_mask` accounts for both phenotype and covariate NaN filtering.

**Risk:** LOW. This is a validation check -- the fix tightens validation, doesn't change computation.

#### Bug 2: LOCO chromosome genotype reads use single-read instead of chunked streaming

**Location:** `loco.py` `_run_lmm_for_chromosome()` lines 305-308

**Current code:**
```python
# Read this chromosome's SNPs from BED file in a single read
bed_file = Path(f"{bed_path}.bed")
with open_bed(bed_file) as bed:
    geno_chr = bed.read(index=np.s_[:, chr_snp_indices], dtype=np.float64)
```

**Problem:** For large datasets (100k+ samples), chromosome 1 can have 20k+ SNPs. A single read allocates `100k * 20k * 8 bytes = 16GB` at once. This is unnecessary because the code immediately filters to valid samples and then processes in JAX chunks. Chunked reading would avoid the full-chromosome allocation.

**Fix approach:** Replace the single `bed.read()` with a chunked iteration that:
1. Reads a chunk of the chromosome's SNPs
2. Applies sample filtering (`valid_mask`)
3. Computes per-chunk statistics (means, miss_counts, vars)
4. After stats pass: reads again in chunks for association (or better: compute stats and association in one pass with the same chunking used by `_prepare_jax_chunk`)

However, the current code does stats computation on the full chromosome genotypes, then filters, then processes in JAX chunks. A simpler approach: read the chromosome genotypes in column-chunked fashion for the stats pass, accumulate stats, then read again in chunks for association. This mirrors what `runner_streaming.py` already does (two-pass: stats then association).

**Complexity:** MEDIUM. This is more than a trivial fix -- it restructures `_run_lmm_for_chromosome` from single-read to two-pass streaming. Can reuse `stream_genotype_chunks` with column subset.

**Risk:** MEDIUM. Must verify numerical equivalence with the single-read path. The column subset + sample filtering + mean imputation must produce identical results.

**Alternative (simpler):** If full restructuring is too complex, use `bed_reader`'s column indexing with row-chunking to avoid the full `(n_samples_total, n_chr_snps)` allocation. The key memory issue is that `geno_chr` is `(n_samples_total, n_chr_snps)` float64 instead of `(n_valid, n_chr_snps)`.

**Note:** `bed_reader.open_bed().read()` already supports column-slice indexing. The quick win is to filter rows at read time: `bed.read(index=np.s_[valid_indices, chr_snp_indices])` to avoid reading samples that will be discarded. But true chunked streaming requires iterating in column chunks.

#### Bug 3: Streaming runner produces no output file when all SNPs are filtered

**Location:** `runner_streaming.py` lines 318-324

**Current code:**
```python
if n_filtered == 0:
    if show_progress:
        elapsed = time.perf_counter() - start_time
        logger.info(f"LMM Association completed in {elapsed:.2f}s (no SNPs passed filter)")
    return []
```

**Problem:** When `output_path` is provided and all SNPs are filtered out, the function returns `[]` before the writer is ever opened (writer setup is at line 376). The caller expects an output file to exist. A valid empty output file should contain the header only.

**Fix approach:** If `output_path` is provided and `n_filtered == 0`, create the output file with header-only before returning. Either:
- Move the writer setup before the n_filtered check
- Or write a header-only file in the `n_filtered == 0` branch

The simpler fix is to write the header-only file inline:
```python
if n_filtered == 0:
    if output_path is not None:
        test_type_map = {1: "wald", 2: "lrt", 3: "score", 4: "all"}
        test_type = test_type_map.get(lmm_mode, "wald")
        with IncrementalAssocWriter(output_path, test_type=test_type) as writer:
            pass  # header written, no data
    return []
```

**Risk:** LOW. No computation logic changes.

#### Bug 4: `snps_indices` set conversion hoisted out of per-chromosome loop

**Location:** `loco.py` `_run_lmm_for_chromosome()` lines 338-343

**Current code:**
```python
# Inside _run_lmm_for_chromosome (called per-chromosome):
if snps_indices is not None:
    snps_set = set(snps_indices.tolist())  # Rebuilt every call
    local_snp_list_mask = np.array(
        [idx in snps_set for idx in chr_snp_indices], dtype=bool
    )
    snp_mask &= local_snp_list_mask
```

**Problem:** `set(snps_indices.tolist())` converts the numpy array to a Python list, then to a set. This is called for every chromosome (19+ times for human data). The set content is identical every time since `snps_indices` is unchanged.

**Fix approach:** Either:
1. Convert to set once in `run_lmm_loco()` and pass `snps_set` to `_run_lmm_for_chromosome` instead of `snps_indices`
2. Or add a parameter `snps_set: set[int] | None` to `_run_lmm_for_chromosome`

Option 1 is cleaner:
```python
# In run_lmm_loco, before the loop:
snps_set = set(snps_indices.tolist()) if snps_indices is not None else None
# Pass snps_set to _run_lmm_for_chromosome
```

**Risk:** LOW. Pure refactoring, no behavioral change.

#### Bug 5: Unused `logls_mle` accumulation in modes that don't use it

**Location:** Multiple files

**In `runner_jax.py`:**
- Line 239: `logls_mle_out = np.empty(n_filtered, dtype=np.float64)` allocated for mode 4
- The mode 4 chunk write section (lines 409-422) does NOT write `logls_mle_out` -- it's dead memory
- BUT: `logls_mle_out` is also unused in `_build_results_all()` (doesn't take a `logls_mle` param)

Wait, re-checking: `_build_results_all` doesn't take `logls_mle`. So `logls_mle_out` is:
- Allocated in mode 2 (line 230): USED correctly (line 407 writes, but then... line 466-472 `_build_results_lrt` doesn't use it either)
- Allocated in mode 4 (line 239): NEVER WRITTEN, NEVER READ

Actually wait, in mode 2 at line 407: `logls_mle_out[s] = np.asarray(best_logls_mle[:slice_len])` -- this writes it. But `_build_results_lrt` doesn't use it. So `logls_mle_out` is computed but not consumed by the result builder in mode 2 either.

**In `runner_streaming.py`:**
- `_ACCUM_KEYS[2]` includes `"logls_mle"` (line 44)
- `_ACCUM_KEYS[4]` includes `"logls_mle"` (line 53)
- `_yield_chunk_results` mode 2 (line 267-273): uses `arrays["lambdas_mle"]` and `arrays["p_lrts"]` but NOT `arrays["logls_mle"]`
- `_yield_chunk_results` mode 4 (line 275-286): does NOT use `arrays["logls_mle"]`

**In `loco.py`:**
- Same pattern: `_ACCUM_KEYS` includes `logls_mle` for modes 2 and 4
- Result building never uses it

**What `logls_mle` is:** It's the per-SNP MLE log-likelihood computed during golden section optimization. It's used to compute `p_lrt` (via `calc_lrt_pvalue_jax`) but is NOT written to the output file. GEMMA's LRT output format is: `chr rs ps n_miss allele1 allele0 af l_mle p_lrt` -- no logl_mle column.

**Fix approach:**
1. Remove `logls_mle_out` allocation from `runner_jax.py` mode 2 and mode 4
2. Remove `"logls_mle"` from `_ACCUM_KEYS[2]` and `_ACCUM_KEYS[4]` in `runner_streaming.py`
3. Remove `"logls_mle": "best_logls_mle"` from `_var_map` in `_append_chunk_results`
4. The variable `best_logls_mle` is still needed as a return value from `golden_section_optimize_lambda_mle` (it returns a tuple), but we can use `_` to discard it

**Wait -- correction:** `best_logls_mle` IS needed to compute `p_lrt`:
```python
p_lrts = jax.vmap(calc_lrt_pvalue_jax)(
    best_logls_mle, jnp.full_like(best_logls_mle, logl_H0)
)
```
So the MLE computation must stay. The issue is only the ACCUMULATION of `logls_mle` into the result arrays. The computation is needed; storing the results is not.

**Fix:** Remove `logls_mle` from `_ACCUM_KEYS` for modes 2 and 4. Remove `logls_mle_out` allocation and write in `runner_jax.py`. Leave the `best_logls_mle` local variable (it's needed for p_lrt computation within the chunk loop).

**Risk:** LOW. Pure dead-code removal. The `logls_mle` values are never consumed.

#### Bug 6: `lmm_mode` validation produces clean ValueError in runner APIs

**Location:** `runner_jax.py` line 488, `runner_streaming.py` (missing), `loco.py` (missing)

**Current state:**
- `runner_jax.py`: Validates at line 488 (after all computation) -- too late
- `runner_streaming.py`: No validation at all
- `loco.py`: `test_type_map.get(lmm_mode, "wald")` silently defaults to "wald" for invalid modes
- `pipeline.py` line 165: Validates in `validate_inputs()` -- correct for CLI path
- `prepare.py` `_compute_null_model()` line 145: Only checks `if lmm_mode not in (2, 3, 4)` -- returns None for mode 1, but doesn't validate invalid modes

**Problem:** If someone calls `run_lmm_association_jax(lmm_mode=5)` or `run_lmm_association_streaming(lmm_mode=5)` directly via the Python API, they get silently wrong results (no mode branch executes) or a late error. The `pipeline.py` validation only protects the CLI path.

**Fix approach:** Add early validation at the top of each runner function:
```python
if lmm_mode not in (1, 2, 3, 4):
    raise ValueError(
        f"lmm_mode must be 1 (Wald), 2 (LRT), 3 (Score), or 4 (All), "
        f"got {lmm_mode}"
    )
```

Add to:
- `run_lmm_association_jax()` (at top, before any computation)
- `run_lmm_association_streaming()` (at top, before any computation)
- `run_lmm_loco()` (at top, before any computation)

Remove the late check at `runner_jax.py` line 488 (now redundant).

**Risk:** LOW. Adding validation, no behavioral change for valid inputs.

#### Bug 7: `test_jamma_vs_gemma_synthetic` raises FileNotFoundError when Docker unavailable

**Location:** `tests/test_kinship_benchmark.py` `test_jamma_vs_gemma_synthetic()` lines 209-254

**Current code:**
```python
def test_jamma_vs_gemma_synthetic(self, test_genotypes):
    # Check Docker is available
    docker_check = subprocess.run(
        ["docker", "info"], capture_output=True, text=True
    )
    if docker_check.returncode != 0:
        pytest.skip("Docker not available")
    # ...
```

**Problem:** If `docker` binary is not installed at all (not just daemon not running), `subprocess.run(["docker", "info"])` raises `FileNotFoundError` instead of returning a non-zero exit code. The test should catch this and skip gracefully.

**Fix approach:**
```python
try:
    docker_check = subprocess.run(
        ["docker", "info"], capture_output=True, text=True
    )
except FileNotFoundError:
    pytest.skip("Docker not installed")

if docker_check.returncode != 0:
    pytest.skip("Docker not available")
```

**Risk:** LOW. Test-only change.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Chunked BED reading | Custom chunk reader in loco.py | `stream_genotype_chunks` or `open_bed` with index slicing | Already exists in `io/plink.py`, battle-tested |
| Output file writing | Manual file.write for header | `IncrementalAssocWriter` context manager | Already handles header format per test type |
| SNP filtering | Custom filter logic | `compute_snp_filter_mask` | Shared, validated filter logic |

## Common Pitfalls

### Pitfall 1: Numerical Regression from Chunked Reads
**What goes wrong:** Changing from single-read to chunked-read genotype loading changes floating-point accumulation order, producing different (within epsilon) results.
**Why it happens:** Floating-point addition is not associative. Different chunk sizes produce different rounding.
**How to avoid:** Ensure the chunked path produces bit-identical results for the same chunk boundaries. Test with multiple chunk sizes against the single-read baseline.
**Warning signs:** Test failures with rtol=1e-13 in existing numerical equivalence tests.

### Pitfall 2: Forgetting to Close Writer on Early Return
**What goes wrong:** The `IncrementalAssocWriter` is opened but not closed if an early return path is hit.
**Why it happens:** The writer uses `__enter__`/`__exit__` manually (not `with` statement) in some paths.
**How to avoid:** Use `with` statement or ensure the `finally` block always runs.
**Warning signs:** Truncated output files, missing newlines.

### Pitfall 3: Sample Count Mismatch Between Eigen Files and Runner
**What goes wrong:** Pre-computed eigen files validated with wrong `n_samples` pass validation but cause dimension mismatch in the runner.
**Why it happens:** The validation uses phenotype-only count, but the runner uses phenotype+covariate count.
**How to avoid:** Compute the combined valid mask before eigen validation.
**Warning signs:** "Eigenvalue count does not match" errors only when covariates have NaN rows.

### Pitfall 4: Changing `_ACCUM_KEYS` Without Updating All Consumers
**What goes wrong:** Removing `logls_mle` from `_ACCUM_KEYS` breaks `_append_chunk_results` or `_concat_jax_accumulators` if they reference the removed key.
**Why it happens:** The accumulator system uses string-keyed dicts; removing a key must be done consistently.
**How to avoid:** Grep for all references to `logls_mle` across the codebase and update each one.
**Warning signs:** KeyError at runtime in modes 2 or 4.

### Pitfall 5: LOCO Chunked Reads Must Handle Column Subset
**What goes wrong:** Using `stream_genotype_chunks` for the LOCO chromosome reads may not directly support column subsetting (chromosome SNP indices).
**Why it happens:** `stream_genotype_chunks` iterates over all SNPs sequentially; it doesn't support reading arbitrary column subsets.
**How to avoid:** Either use `open_bed` with explicit column+row indexing in chunks, or adapt the streaming approach to work with column subsets.
**Warning signs:** Reading all SNPs instead of just the chromosome's SNPs, wasting I/O.

## Open Questions

1. **LOCO chunked reads: full restructure or quick win?**
   - What we know: `stream_genotype_chunks` iterates all SNPs; LOCO needs only one chromosome's columns
   - What's unclear: Whether `bed_reader` supports efficient column-subset + row-subset chunked reads
   - Recommendation: Use `open_bed` with combined row+column indexing. For each chunk of chromosome columns, read `bed.read(index=np.s_[valid_indices, chr_snp_indices[start:end]])`. This avoids reading filtered-out samples AND reads in column chunks.

2. **Should `logls_mle` be removed from mode 2 accumulation too?**
   - What we know: Mode 2 computes `best_logls_mle` (needed for p_lrt), stores it in accumulators, but `_yield_chunk_results` mode 2 never reads `arrays["logls_mle"]`
   - What's unclear: Whether any downstream consumer might want `logls_mle` for diagnostics
   - Recommendation: Remove from accumulation. The value is a per-SNP diagnostic that GEMMA doesn't output. If needed later, it can be re-added.
